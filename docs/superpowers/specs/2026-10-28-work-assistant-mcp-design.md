# Дизайн: Work Assistant как MCP-сервер

Дата: 2026-10-28  
Статус: согласован в диалоге; ожидает review письменной спецификации

## Цель

Заменить пользовательские действия GUI вызовами локального MCP-сервера. Агент
использует MCP для чтения worklog'ов и git-коммитов, составляет предложения
своей моделью, а сервер валидирует их и записывает в Redmine или YouTrack
только после обязательного подтверждения пользователя через MCP elicitation.
Ключи AI-провайдера серверу не нужны.

Изменение выполняется раньше удаления GUI. GUI-removal описан отдельной
спецификацией и начинается только после проверки MCP-сценариев.

## Согласованные решения

| Тема | Решение |
| --- | --- |
| Транспорт | Локальный MCP stdio-сервер |
| AI-анализ | Выполняет агент на стороне пользователя; сервер не хранит AI-ключи |
| Конфиг пользователей | `config/users.json`, исключённый из Git |
| Выключенные пользователи | `is_enable: false` — не показывать и не использовать |
| Апрув записи | MCP elicitation для конкретного плана; отказ/неподдержка блокирует запись |
| Redmine issue ID | Обязателен в каждом запросе на запись в Redmine; не брать из JSON |
| YouTrack issue ID | Хранится в JSON пользователя и используется для записи в YouTrack |
| YouTrack → Redmine | Суммировать по юзеру и дате; комментарий из JSON; не создавать дубликат |
| Git-путь | Передаётся в MCP-вызове и не сохраняется |
| Skills | MCP объявляет только перечисленные инструменты и не вызывает skills |

## Архитектура

```text
OpenCode / MCP host
  └── локальный MCP stdio server (проектная конфигурация, codemode=false)
        ├── read-only config loader → config/users.json
        ├── tracker clients → Redmine / YouTrack
        ├── GitClient → чтение коммитов из переданного репозитория
        └── staged write plans → MCP elicitation → approved tracker writes
```

Сервер переиспользует существующие tracker/client слои там, где их контракты
подходят. Вызовы git ограничены чтением репозитория: MCP принимает путь и
период, проверяет git worktree и не принимает произвольные команды.

OpenCode V2 поддерживает локальные stdio MCP-серверы и elicitation. Проектная
конфигурация показывает MCP-инструменты напрямую (`codemode: false`). Сервер
не регистрирует MCP prompts, resources или `instructions`; он не инициирует
загрузку skills, не вызывает другие MCP-серверы и не запускает субагентов.
Выбор skills самим MCP host остаётся под контролем host и не может быть
ограничен сервером.

## Конфиг и секреты

`config/users.json` — локальный файл проекта, добавленный в `.gitignore`.
В репозитории хранится только пример без секретов. Форма файла:

```json
{
  "users": [
    {
      "name": "Имя",
      "is_enable": true,
      "git_email": "author@example.com",
      "redmine": {
        "api_key": "",
        "user_id": 1,
        "activity_id": 1,
        "comment": "development"
      },
      "youtrack": {
        "access_token": "",
        "issue_id": "PROJECT-1"
      }
    }
  ]
}
```

URL Redmine и YouTrack остаются в `.env`. `redmine.issue_id` намеренно не
является источником настройки: пользователь передаёт ID задачи заново для
каждой записи, потому что задача меняется каждый месяц. `youtrack.issue_id`
нужен только как назначение для сценария дозаполнения YouTrack.

Конфиг читается без исполнения кода; некорректный или отсутствующий файл
останавливает подготовку плана. Рекомендуемые права файла — `0600`. Токены не
возвращаются MCP-инструментами и не попадают в логи или сообщения об ошибках.
Если юзер не указан и включён ровно один профиль, можно выбрать его; если
включено несколько, агент должен запросить имя. Отключённый профиль нельзя
выбрать даже по имени.

## MCP-инструменты и сценарии

Инструменты разделены на чтение, подготовку и подтверждённую запись.
Подготовка не вызывает POST. Имена ниже задают контрактную форму; детали
аргументов должны соответствовать существующим DTO и быть типизированы в
реализации.

### Общие read-only инструменты

- `list_enabled_users` — имена и доступные источники/назначения без секретов.
- `get_worklogs(user, tracker, start, end)` — даты, часы, комментарии и
  issue без ключей авторизации.
- `get_git_commits(user, repo_path, start, end)` — коммиты автора из JSON
  (`git_email`) в переданном репозитории; только выбранный период.

### 1. Добрать 8 часов в Redmine

`prepare_redmine_autofill(user, date, issue_id)`:

1. Обязательный `issue_id` берётся только из текущего запроса; если пользователь
   не передал его, агент сначала спрашивает.
2. Сервер читает все часы пользователя в Redmine за дату независимо от issue.
3. Предлагает только положительную разницу до 8 часов и использует
   `redmine.comment` из JSON.
4. Если день уже заполнен до 8 часов или выше, пустой план не записывается.

### 2. Перенести YouTrack → Redmine

`prepare_youtrack_transfer(user, start, end, issue_id)`:

1. `issue_id` Redmine обязателен в каждом запросе; если он отсутствует, агент
   спрашивает пользователя. Старое значение из JSON/SQLite не используется.
2. Worklog'и YouTrack агрегируются по дате в одну запись на юзера за день.
3. Комментарий — `redmine.comment` этого юзера.
4. До подготовки сервер читает записи целевого Redmine issue. Точное совпадение
   пользователя, даты, issue, часов и комментария помечается как уже перенесённое
   и пропускается. Неполное/конфликтующее совпадение показывается в плане и не
   превращается автоматически в дополнительную запись.

### 3. Дополнить YouTrack по коммитам

Агент вызывает `get_worklogs` для YouTrack и `get_git_commits` с переданными
папкой и периодом, анализирует их своей моделью и подготавливает дневные
предложения. Затем `prepare_youtrack_fill(user, repo_path, start, end, entries)`:

1. Сервер заново читает YouTrack и коммиты для проверки предложения.
2. Назначение — `youtrack.issue_id` из активного JSON-профиля.
3. Предложения допускаются только для дат с коммитами; часы положительные,
   кратны 0.5 и вместе с уже залогированными часами не превышают 8 часов за день.
4. Комментарий для работы по коммитам формирует агент. Переданные hash'и должны
   существовать в коммитах выбранного автора и периода.

Сервер не вызывает AI-провайдер, не придумывает объяснения по коммитам и не
требует отдельного AI API key.

## Подтверждение и запись

Каждый `prepare_*` возвращает неизменяемый `plan_id`, точную сводку записей,
целевой трекер и целевые issue. Он не пишет данные. Инструмент
`write_plan(plan_id)`:

1. отклоняет неизвестный, просроченный или уже использованный план;
2. через MCP elicitation показывает точные юзера, даты, часы, комментарии и
   issue и требует явного положительного ответа;
3. при отказе, закрытии формы или отсутствии поддержки elicitation не делает
   ни одного POST;
4. при согласии пишет только неизменённые строки плана один раз и возвращает
   результат по каждой строке.

Планы хранятся только в памяти процесса, одноразовые и действуют 10 минут;
перезапуск MCP-сервера их аннулирует. Подтверждение одно на всю показанную
сводку. Запись по HTTP не транзакционна: при сбое возможен частичный успех,
который сервер обязан явно отразить в результате.

## Ошибки и безопасность

- Ошибка конфигурации, отсутствующие credentials, неактивный/неоднозначный
  юзер, неверный период или отсутствующий Redmine `issue_id` дают понятную
  ошибку без записи.
- У каждой ошибки обрезаются потенциальные фрагменты токенов/заголовков.
- HTTP-записи идут только в Redmine/YouTrack endpoints из конфигурации; MCP не
  предоставляет generic HTTP, shell, filesystem-write или произвольный tool.
- Git используется для валидации репозитория и чтения логов; любые параметры
  команд формируются сервером, а не принимаются как shell-строка.
- Успешные строки после частичной ошибки видны в результате, а следующий
  перенос пропускает точные уже существующие совпадения.

## Проверки

Покрыть тестами:

- загрузку JSON, ошибки схемы, `is_enable`, выбор профиля и отсутствие секретов
  в результатах/логах;
- все три prepare-сценария, расчёт остатка до 8 часов и правила issue;
- агрегацию YouTrack, комментарий, дубликаты и конфликты переноса;
- проверку commit hashes/дат и лимита часов для YouTrack fill;
- отсутствие POST во всех read/prepare путях, при отказе и недоступности
  elicitation;
- один успешный POST на строку только после согласия, одноразовость плана,
  истечение плана и корректный отчёт при частичной ошибке;
- список MCP-возможностей содержит только задекларированные tools, без
  prompts/resources/server instructions.

## Этапы

Локальные базы, игнорируемый JSON и другие пользовательские файлы при этих
