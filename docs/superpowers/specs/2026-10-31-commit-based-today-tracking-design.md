# Дизайн: трекинг дня по коммитам

Дата: 2026-10-31
Статус: согласован в диалоге

## Цель

Дать пользователю MCP-режим «затрекай сегодня»: по умолчанию 8 часов за
сегодняшний день, распределённые по issue из git-коммитов пропорционально
интервалам между коммитами. Тот же расчёт должен использоваться всегда, когда
пользователь просит затрекать время на основе коммитов.

## Решения

| Тема | Решение |
| --- | --- |
| Новый tool | `prepare_youtrack_from_commits` |
| Период по умолчанию | только сегодня |
| Часы по умолчанию | 8.0 за день, включая daily meeting |
| Распределение | интервалы между коммитами |
| Начало дня | `youtrack.workday_start`, по умолчанию `09:00` |
| Округление | до 0.5 часа, сумма точно равна доступному остатку |
| Уже записанные часы | вычитаются из 8 |
| Daily meeting | добавляется автоматически, если настроен и ещё не записан |
| Нет коммитов | fallback на `youtrack.issue_id` |
| Нет issue в коммитах | fallback на `youtrack.issue_id` |
| Запись | только через существующий `write_plan` + elicitation |

## Контракт tool

```text
prepare_youtrack_from_commits(
    user_name: str,
    repo_path: str,
    start: str | None = None,
    end: str | None = None,
    daily_hours: float = 8.0,
) -> dict
```

- Без `start`/`end` период — `today..today`.
- `daily_hours` — целевая сумма за день, положительная, не больше 8.
- Tool ничего не пишет, возвращает `plan_id`, `period`, `entries`, `warnings`.
- Формат `entries` совпадает с `prepare_youtrack_fill`, чтобы `write_plan` не
  менялся.

## Алгоритм распределения

Для каждого дня:

1. Читаются существующие worklog'и YouTrack; `remaining = daily_hours -
   existing_hours`.
2. Если `remaining <= 0`, день пропускается с warning.
3. Если настроен daily meeting, день рабочий и meeting ещё не записан,
   добавляется отдельная запись на `daily_meeting_hours`; remaining
   уменьшается.
4. Коммиты дня сортируются по времени.
5. Вес коммита — время от предыдущего коммита (или от `workday_start`) до
   текущего. Вес меньше минуты поднимается до минуты, чтобы коммит не потерялся.
6. Issue берутся из subject и body коммита. Если issues несколько, вес делится
   между ними поровну. Если issue нет, используется fallback issue; если
   fallback нет, интервал пропускается с warning.
7. Веса агрегируются по issue и масштабируются на `remaining`.
8. Результат округляется до 0.5 часа методом largest remainder. Каждая issue
   получает минимум 0.5 часа, если доступных получасов хватает; иначе
   отбрасываются issue с наименьшим весом и добавляется warning.
9. Комментарий — subject последнего коммита по issue. Для fallback без
   коммитов — `youtrack.default_comment` (по умолчанию `development`).

Последний коммит не получает время после себя: конец рабочего дня неизвестен.

## Пример

Коммиты: `A` в 10:00, `B` в 13:30, `A` в 17:00. Начало дня 09:00.
Веса: `A` = 60 + 210 = 270 минут, `B` = 210 минут. На 8 часов:
`A` = 4.5 ч, `B` = 3.5 ч.

## Ошибки и безопасность

- Нет коммитов и нет fallback issue — ошибка для одиночного дня; для периода
  день пропускается с warning.
- Некорректный `workday_start`, `daily_hours`, issue ID или дата — понятная
  ошибка без записи.
- Токены и заголовки авторизации не попадают в результат.
- `prepare_*` не делает POST; запись только после явного approval.

## Переименование репозитория

- Локальная папка: `fill_redmine` → `work-assistant`.
- README, AGENTS и remote URL обновляются на `work-assistant`.
- GitHub-репозиторий переименовывается отдельно: локальный агент без `gh` или
  токена не может это сделать. После переименования на GitHub remote URL
  обновляется на `git@github.com:olelit/work-assistant.git`.

## Проверки

- unit-тесты распределения: интервалы, несколько issue в коммите, нулевые
  интервалы, fallback, округление, лимит 8.
- MCP-тесты: период по умолчанию сегодня, 8 часов, существующие часы, daily
  meeting, нет коммитов, fallback, отсутствие записи в prepare, успешная запись
  через `write_plan`.
- Полный `pytest -q`.
